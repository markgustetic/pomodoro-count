# README visual pass

**Date:** 2026-07-31
**Status:** implemented in this commit.

A design pass on README.md so the page looks like the app it documents, within
what GitHub actually renders.

## The constraint that shapes everything

GitHub sanitizes markdown: no CSS, no `style` attributes, no fonts, no coloured
text. What survives is `<picture>` with `prefers-color-scheme`, `<img>` with
`width`/`align`, tables, and shields.io badge URLs. So "closer to the app's
style" cannot mean restyling type or surfaces. It has to be carried by the two
things the page can control: **which screenshots appear**, and **badge colour**.

That turns out to suit this app, because its most distinctive visual fact is
that it ships two themes — and a README can demonstrate that rather than assert
it.

## Decisions

### Theme-aware hero

The hero becomes a `<picture>`: `panel-classic.png` for a reader in light mode,
`panel-synthwave.png` for a reader in dark mode. Both files exist and were
re-rendered from the 1.4.0 bundle on 2026-07-31.

The point is not novelty. A reader in dark mode currently gets a bright white
panel dropped into a dark page, which looks like a screenshot of a different
application. Matching the reader's appearance removes that, and the app's
two-theme feature demonstrates itself on the way past.

### Two themes, shown side by side

Making the hero swap creates a problem: a light-mode reader would never learn
Synthwave exists, and a dark-mode reader would meet it twice. So the standalone
Synthwave screenshot under "Two themes" is replaced by a **cropped pair** —
both Focus tabs, side by side, as `docs/theme-classic.png` and
`docs/theme-synthwave.png`.

Cropping to the Focus tab is what makes this legible. The full renders are
1944px triptychs; at half width a whole three-tab panel is unreadable, while a
single tab is comfortable. The crop box is x24 y24 624×1096, chosen as the
union of both themes' detected content bounds — Synthwave's neon bleeds ~28px
wider than Classic's, so a box fitted to Classic alone would clip its glow.

**Two files rather than one composite,** which is the opposite of the first
instinct. A single side-by-side image guarantees alignment, but it also scales
as one unit: on a phone a 1332px composite shrinks to the container and each
panel lands around 180px, illegible. Two images at `width="400"` sit side by
side on desktop and wrap to one-per-line on a narrow screen, each still
readable.

Generated by `Tools/make-theme-shots.sh`, not by hand, so it can be regenerated
when the panel changes. The panel screenshots have already gone stale once (the
1.4.0 doc sweep found both showing a retired control), and a derived image that
nobody can regenerate goes stale faster than its source. The script uses `sips`
rather than Python: it ships with macOS, this repo has no Python dependency to
justify adding one for a crop, and its output was checked byte-identical to the
equivalent Pillow crop before committing to it.

### Badges: one accent, everything else neutral

- **The CI badge is not touched.** Its colour is *semantic* — green means the
  build passes, red means it does not. Styling it to a brand colour would
  destroy information to gain decoration. This is the one badge on the page
  that is carrying data.
- **The release badge** takes the Classic accent, `#E03830`.
- **macOS and license badges** become neutral grey.

This deviates slightly from the shape first described, which had all three
static badges in the accent. One accent against neutrals is truer to the app:
Classic is neutral surfaces with a single red, and three identical red badges
in a row of four reads as flat rather than styled. Same reasoning as the
palette rule about not putting two neon light sources in one card.

Badge *style* stays at shields.io's default, because the GitHub Actions badge
beside it cannot be restyled and mixing styles looks worse than any colour
choice fixes.

### "Using it" regrouped

The section is ten consecutive bold-lead paragraphs with no subheadings — the
page's real readability problem, and a layout one rather than a writing one.
Four `###` subheadings, with **every sentence keeping its exact wording**:

| Heading | Absorbs |
|---|---|
| Logging a pomodoro | the log button, the global hotkey, the URL scheme |
| The menu bar | menu-bar-only orientation, right-click to quit, what the icon shows |
| The built-in timer | timer configuration, the break that waits |
| History and categories | charts and tooltips, CSV export, category rows and `±` |

Streaks, VoiceOver and Two themes stay as trailing paragraphs. They are
one-liners; a heading each would be more structure than they carry.

## Out of scope

- **Prose rewriting.** The voice is specific and good — "the tally that hardware
  is missing" earns its place — and a visual pass that quietly reworded things
  would be much harder to review than it looks.
- **Emoji headers and `> [!NOTE]` callouts.** Both read as GitHub-template
  decoration rather than as this app's design language.
- **Any content change.** Nothing here alters a claim about behaviour. The
  1.4.0 doc sweep already corrected those.

## Verification

- Both themes' crops render legibly and identically sized — checked by eye
  before committing, not just by dimensions matching.
- Every `<img>` path in the README resolves to a file that exists.
- No sentence removed from "Using it": word-count and a diff read confirm the
  regrouping moved text rather than editing it.
